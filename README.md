## The thesis

Anyone can generate a talking head. The hard part is everything that has to be true *around* it: that the face belongs to someone who consented, that the words are supported by a document, that the performance can improve without the person changing, and that a year from now you can prove all three.

AVATAROS treats those guarantees as the product. A digital actor is defined by an immutable **Digital DNA** record and bound to a signed **likeness-rights** grant. Every production runs through a **fail-closed Publication Gate** that will refuse to ship. And every decision the system makes — every claim it verified, every render it blocked, every analytical query an agent ran — is appended to ClickHouse and read back through the **official `mcp-clickhouse` MCP server**.

That last part is the non-obvious move. ClickHouse is not a chart on the side of this product; it is the ledger the product is accountable to. "Why was this promo blocked?" is a `SELECT` with a reason code and a trace id. Even the panel that proves partner usage is itself fed by partner usage — reading the MCP call ledger *is* an MCP call, so the evidence is generated by the thing it evidences.

**The loop can change how the actor performs. It can never change who they are.**

## Who this is for

**Priya, campaign lead at a consumer-electronics brand's in-house studio.**

Her team has a signed likeness agreement with one presenter, Maya, valid for product marketing in specific regions until a fixed expiry. She needs to ship a 60-second launch promo in English and Hindi, plus vertical cutdowns for three platforms.

**What it costs today.** Re-shooting for each variant means a studio day, a crew, and the presenter's calendar — roughly two weeks from brief to delivery per language. Worse, every spoken performance claim ("40% faster inference") has to be manually checked against engineering documentation by someone in legal, because if the number is wrong it is the *brand* that made a false advertising claim, in the presenter's voice, wearing their face.

**What changes.** The brief goes in once. The system retrieves the supporting documentation, refuses to script any claim it cannot ground in a source passage, renders both languages against the same locked identity, verifies the rendered output actually matches the approved script, and blocks publication if any check fails. What legal receives is not a video and a promise — it is a video and a queryable decision record.

**What it does not do.** It does not negotiate the rights agreement, and it does not replace legal sign-off. It makes the sign-off cheap, fast, and evidenced.

## How ClickHouse is actually used at runtime

The track requires runtime use of ClickHouse via the official `mcp-clickhouse` server. Here is precisely how that works, and how to check it yourself.

```
┌──────────────────────────────────────────────────────────────────────┐
│  AVATAROS backend process                                            │
│                                                                      │
│   Agents ──► MCP Governance Gateway ──► governed SQL templates        │
│  (evolution,   • per-agent allowlist     (agents supply typed args,   │
│   director,    • no raw SQL, ever         never SQL)                  │
│   research)    • writes call ledger                                   │
│                          │                                            │
└──────────────────────────┼────────────────────────────────────────────┘
                           │  MCP protocol (JSON-RPC over stdio)
                           ▼
              ┌─────────────────────────────┐
              │  mcp-clickhouse  v0.6.0     │   ← the official server,
              │  tools: list_databases,     │     installed unmodified
              │         list_tables,        │     in its own virtualenv
              │         run_query           │     (read-only mode)
              └─────────────┬───────────────┘
                            │ HTTPS
                            ▼
              ┌─────────────────────────────┐
              │  ClickHouse Cloud           │
              │   scene_events              │  audience telemetry
              │   strategy_versions         │  strategy lineage
              │   mcp_tool_calls            │  MCP call ledger
              │   governance_events         │  immutable decision audit
              └─────────────────────────────┘
```

**Reads** go out over MCP. **Writes** (telemetry, ledger appends) go direct over `clickhouse-connect`, because the partner server is deliberately held in read-only mode — an agent cannot mutate telemetry even if it found a way past the template layer.

### Why agents get templates instead of SQL

`run_query` takes an arbitrary SQL string. Handing that to an autonomous agent is handing it arbitrary SQL. So AVATAROS never does: each tool an agent may call maps to exactly one parameterized template in [`backend/app/mcp/sql_templates.py`](backend/app/mcp/sql_templates.py). The agent supplies typed arguments, which are validated and escaped before rendering. An agent cannot express a query that is not already written down.

This makes the permission matrix load-bearing rather than decorative — Live Mode is denied analytics access because the gateway will not compile a template on its behalf:

| Agent identity | May call |
|---|---|
| `evolution_agent` | strategy performance, scene performance, version comparison, governance summary |
| `director_agent` | scene performance only |
| `research_agent` | claim-verification metrics only |
| `governance_console` | the two ledgers (read-only observability) |
| `live_session`, `script_agent`, `critic_agent` | **nothing** |

### Verifying it yourself

Open **ClickHouse & MCP → MCP Trace** in the app. Every partner call appears live with its agent identity, the exact SQL it compiled to, the row count, and the measured latency. Click **Verify from ClickHouse** to re-read the ledger out of the cluster through the MCP server — the panel shows you the query that fetched it and the server that ran it.

Or from a terminal:

```bash
curl -s localhost:8080/api/mcp/trace/verify | python3 -m json.tool
```

## Governance demos

The failure paths are the point. Each of these runs end to end and writes its decision to the governance ledger:

| Demo | What it proves |
|---|---|
| `POST /api/production/demo/claim-block` | A spoken claim with no supporting document passage is blocked before render. |
| `POST /api/production/demo/guardian-failure` | Rendered output that drifts from the approved emotional plan is caught and reworked. |
| `POST /api/production/demo/rights-block` | An expired likeness grant halts production immediately — no render, no exceptions. |

After running any of them, open **Governance Ledger** and filter to `BLOCK`. Every refusal is a row with a reason code, a trace id, and the run it belongs to.

## Honest provider matrix

The app reports which subsystems are backed by a real service and which are running the deterministic offline engine, and labels them as such in the UI. It is not decoration — the badge in the header reads the live runtime, so an unreachable cluster shows as unavailable rather than green.

| Subsystem | Real provider | Offline fallback | Notes |
|---|---|---|---|
| Analytics transport | **official `mcp-clickhouse` v0.6.0** | deterministic adapter | stdio MCP; readiness probes the cluster, not just the handshake |
| Telemetry store | **ClickHouse Cloud / self-hosted** | in-memory simulation | 4 tables, see [`init_clickhouse.sql`](backend/init_clickhouse.sql) |
| Agent reasoning | **Google Gemini (`gemini-3.6-flash`)** | deterministic rule engine | live; model ID resolved against the API at runtime with fallbacks |
| Live conversation | Gemini Live API | **Gemini turn-based** → deterministic cascade | turn-based tier is live and labelled "not realtime" in the UI |
| Guardian / ASR | Gemini multimodal | **ffprobe media inspector (active)** | deliberately deterministic — see note below |
| Voice | **Gemini native TTS (`gemini-2.5-flash-preview-tts`)** | deterministic tone synth | real speech; delivery steered by the Director's emotional target |
| Renderer | neural (integration point) | **deterministic ffmpeg (active)** | identity-locked compositing |
| Media storage | Google Cloud Storage | local filesystem | set `MEDIA_STORAGE_PROVIDER=gcs` + bucket; a misconfigured bucket reports `degraded`, it does not silently fall back |

**Where a fallback is active, the UI says so.** No number rendered in this app is a placeholder: if a query returns no rows, the panel says *no data*. Seeded demo telemetry is labelled as seeded.

> **On ASR and the multimodal Guardian.** Both have working Gemini code paths and
> a valid key, and both are currently left on the deterministic engine. With real
> TTS now in place, Gemini ASR does transcribe the rendered audio accurately —
> a round trip through synthesis and back returns the spoken script — but the
> visual Guardian inspects HUD composites rather than faces, so enabling it would
> fail identity similarity and block every run. ASR is enabled with
> `ASR_PROVIDER=gemini`; the visual Guardian waits on a real likeness renderer.

> **On the renderer.** The default `RENDERER_PROVIDER=ffmpeg` path is a
> deterministic compositor: it produces a real, verifiable MP4 per scene carrying
> the identity-lock badge, scene header, spoken line, emotion readout and an audio
> waveform, and every clip is SHA-256 hashed into the provenance record. It does
> not synthesize a face. Photoreal rendering is a documented integration point
> (`RENDERER_PROVIDER=neural_liveportrait` plus `RENDERER_API_KEY`) that requires a
> licensed likeness source — which is the same constraint the product enforces on
> its users, so shipping a face without one would contradict the thesis.

> **On the seed data.** `scene_events` is populated with generated demo telemetry (a v13 exploration period across four hook arms, and a v14 post-deployment cohort) so the evolution loop has something real to compute over. The rows are synthetic; every statistic derived from them is genuinely computed by ClickHouse and a real Welch's t-test, not stored.

## Quickstart

Two commands, from a clean clone. Requires Docker.

```bash
docker compose up --build
```

```bash
open http://localhost:8080
```

That brings up ClickHouse, applies the schema, seeds demo telemetry, and starts AVATAROS with the official MCP server wired in. The app serves the SPA and the API from one origin on port 8080.

To run the agent chain on Gemini instead of the deterministic engine:

```bash
GEMINI_API_KEY=your-key AI_PROVIDER=gemini docker compose up --build
```

<details>
<summary><b>Local development without Docker</b></summary>

```bash
# Backend + the official MCP server (two virtualenvs, on purpose - see below)
uv venv backend/.venv --python 3.11
uv pip install --python backend/.venv/bin/python -r backend/requirements.txt
uv venv backend/.mcp-server-venv --python 3.11
uv pip install --python backend/.mcp-server-venv/bin/python -r backend/requirements-mcp-server.txt

# A ClickHouse to talk to
docker run -d --name avataros-clickhouse -p 18123:8123 \
  -e CLICKHOUSE_DB=avataros -e CLICKHOUSE_USER=avataros \
  -e CLICKHOUSE_PASSWORD=avataros_dev_pw \
  clickhouse/clickhouse-server:24.8-alpine

cp .env.example .env   # then set CLICKHOUSE_* and MCP_PROVIDER=clickhouse_mcp
backend/.venv/bin/python -m backend.app.data.seed_clickhouse

PYTHONPATH=. backend/.venv/bin/python -m uvicorn backend.app.main:app --port 8000
npm --prefix frontend install && npm --prefix frontend run dev   # http://localhost:3000
```

**Why two virtualenvs.** `mcp-clickhouse` depends on fastmcp 4 → starlette 1.x, while this application pins FastAPI 0.115 → starlette 0.4x. Installing both in one environment breaks FastAPI. Isolating the server keeps both dependency trees valid *and* keeps the partner server a genuinely separate process reached over a real protocol, which is the point.

</details>

## Tests

```bash
backend/.venv/bin/python -m pytest backend/tests -q
```

Runs fully hermetic — in-memory telemetry, deterministic MCP adapter, no network — so it passes on a clean clone with no cluster. Includes regression guards that fail the build if a hardcoded analytics constant ever reappears in the adapter layer, or if a significance verdict is asserted rather than computed.

To exercise the real partner path against a live cluster:

```bash
AVATAROS_INTEGRATION_TESTS=1 backend/.venv/bin/python -m pytest backend/tests/integration -v
```

These assert that the server identity is `mcp-clickhouse`, that reported metrics are reconstructable from returned rows, that a refused call still reaches the ledger, and that the partner server rejects writes.

## Deploying

Single Cloud Run service, single public URL, secrets in Secret Manager.

```bash
PROJECT_ID=your-project \
CLICKHOUSE_URL=https://<id>.<region>.gcp.clickhouse.cloud:8443 \
CLICKHOUSE_PASSWORD=... \
GEMINI_API_KEY=... \
./deploy/cloud_run_deploy.sh
```

The script is idempotent, creates the registry and secrets if missing, and finishes by polling `/health` until the MCP partner reports ready — it fails loudly rather than reporting a green deploy over a broken connection.
